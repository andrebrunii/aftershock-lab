# Experiments to make the project yours

Use a separate branch for each experiment. Record a prediction before running code, then the observed result, limitation and decision. Do not invent historical commits or results.

## 1 — A negative control: a legitimate sensitive-path request

Create `experiment/legitimate-sensitive-path`. In a copy of the shared-NAT scenario, add 30 legitimate requests to `/.env`, representing a badly designed but currently used integration. Predict the collateral fraction for `narrow_control` before running it. With 930 benign requests, the loss is 30/930, approximately 3.23%; the default 2% budget should reject it. This demonstrates that the supposedly precise control is only safe under the fixture assumptions.

Keep the original fixture unchanged, add a new scenario and a regression test. Explain why blocking a sensitive path is not universally safe.

A small sensitivity sweep is already implemented as a reference: `python -m aftershock.sensitivity`. It writes `output/sensitivity.csv`; the recorded baseline is `examples/sensitivity.csv`. Eligibility changes between 18 additional affected legitimate requests (18/918, about 1.96%) and 19 (19/919, about 2.07%). Your own extension should change an assumption beyond this existing test.

## 2 — Remove a dependency and find the modeling error

Copy the payment scenario. Remove the checkout-to-payments dependency and compare the collateral of isolating payments. The model now undercounts affected checkout traffic. The code cannot discover an omitted real-world dependency if the remaining graph is valid. Document that this is an input-model limitation, not a property solved by the gate.

## 3 — Compare value-only undo with revision-aware undo

In a test-only function, attempt rollback if the current value equals the transaction's after value, ignoring revisions. Reproduce `true → false → true` after the initial action. The naive condition passes; the implemented rollback refuses. Keep the unsafe function in test code only and explain the ABA case in your own words.

## 4 — Test the exact collateral boundary

Build a separate fixture with exactly 2 newly denied legitimate requests out of 100; the collateral check should pass. At 3/100 it should fail. Test counts directly, rather than a rounded UI percentage. Consider integer cross-multiplication if you extend the engine to very large counts and need to avoid floating-point threshold comparisons.

## 5 — Run the optional model honestly

Use `OLLAMA.md` to compare clean and poisoned context. Preserve invalid answers and no-change outcomes. Explain why a well-formed JSON proposal is not necessarily a safe proposal. Never label fixture outputs as generated by a model.

## 6 — Extend with TTL, then challenge the undo

Design a temporary control that expires after an explicit simulated time. Who owns the rule if another operator renews it before expiry? An expiry worker must not blindly remove a newer rule. Add revision-aware expiration tests before adding a scheduler. This is an implementation exercise, not a feature already present.
